### ⚠️ PFLICHT ZUERST: persistierten Session-Report anlegen

Der Session-Report ist ein **Repo-Artefakt**, kein reiner Chat-Text. Er MUSS als
Datei existieren, im Auslieferungs-ZIP liegen und verifiziert werden — sonst gilt
die Session als NICHT abgeschlossen. (Genau hier ging früher session-002.md
verloren: das CHANGELOG wurde gepflegt, die Session-Datei nie geschrieben.)

Regeln:
1. **Eine Datei je Session:** `docs/sessions/session-<NR>.md` (nullpadded, z. B.
   `session-003.md`). NIEMALS an die Datei einer früheren Session anhängen.
2. Der Report wird mit den unten stehenden Abschnitten **vollständig ausgefüllt**
   (keine leeren `[ ]`-Platzhalter in der Auslieferung).
3. Die Datei wird **in das gelieferte ZIP aufgenommen** (Clean-Install-Paket
   enthält sie; bei Patch-ZIP explizit mitliefern — cp überschreibt nur, löscht
   nie, also Datei bewusst aufnehmen).
4. **Existenz-/Inhalts-Gate vor „fertig":**
   ```bash
   test -s /home/claude/vimipad/docs/sessions/session-<NR>.md \
     && grep -q "Testlauf-Ergebnis" /home/claude/vimipad/docs/sessions/session-<NR>.md \
     && echo "SESSION-DOC OK" || echo "FEHLT – Session NICHT abschließen"
   # und: im ZIP enthalten?
   unzip -l <ausgeliefertes.zip> | grep "session-<NR>.md" || echo "NICHT IM ZIP"
   ```
5. Bei sehr langen/kompaktierten Sessions ohne klares Ende: den Report **laufend**
   (spätestens bei jedem Versionsbump) fortschreiben, damit er nie an einem
   einzelnen „Session-Ende"-Ereignis hängt.
6. Falls die Verifikation eine echte Umgebung erforderte, die nicht lief: das
   ehrlich im Testlauf-Ergebnis vermerken (nicht Erfolg vortäuschen).

Erst wenn das Gate „SESSION-DOC OK" **und** „im ZIP" meldet, folgen die
Carry-forward-Zeilen für die nächste `sessionstart.txt` (Abschnitt ganz unten).
Diese Carry-forward-Zeilen ERSETZEN den persistierten Report NICHT.
