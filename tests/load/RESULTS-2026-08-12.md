# mod_vimipad — load test results, 2026-08-12

Both runners drove the read-heavy web-service functions against a seeded large
map (1000 nodes / 2000 relations / 200 containers, 5000-row operation log) at
**25 concurrent users**. JMeter ran ~90 s, k6 60 s.

## Headline

**Both runs passed with zero errors.** No web-service exception, no non-200, in
26 478 requests combined. Throughput was ~172–177 requests/s in both tools, which
is close enough to treat the two as measuring the same system rather than two
different ones.

| | JMeter | k6 |
| --- | --- | --- |
| Requests | 15 942 | 10 536 |
| Throughput | 176.8/s | 171.3/s |
| Errors | 0 (0.00 %) | 0 (0.00 %) |
| Mean | 131 ms | 145 ms |
| Max | 769 ms | 4 290 ms |

## Per endpoint (k6)

| Endpoint | median | p95 | max |
| --- | --- | --- | --- |
| `get_layout_history` | 58 ms | 112 ms | 662 ms |
| `get_operations` | 76 ms | 146 ms | 703 ms |
| `get_revision_state` | 104 ms | 197 ms | 756 ms |
| `get_workspace` | **281 ms** | **550 ms** | **4 290 ms** |

`get_workspace` is roughly **3–5× more expensive than every other read**, and it
owns the entire tail: the global maximum of 4.29 s is a `get_workspace` call, and
it is the only endpoint that missed its budget — 13 of 2634 calls (0.5 %) went
over, which is why the `under budget` check landed at 99 % while every other
check was clean.

This is not surprising and not, on this evidence, a defect. `get_workspace`
returns the whole map: 1000 nodes, 2000 relations and 200 containers in one
response. The other three return deltas or history slices. The 1.2 GB of data
received across the k6 run — ~19 MB/s — is essentially this endpoint.

## What this does and does not tell us

**Does:** the read path is functionally sound under concurrency (zero exceptions
across 26 478 requests), throughput is stable, and the keyset pagination
introduced in 0.9.14 did not introduce a regression — `get_operations` sits
comfortably at a 76 ms median against a 5000-row op-log.

**Does not:** this was a single load level on one machine. There is no baseline
from before the 0.9.14/0.9.15 changes to diff against, so these numbers establish
a **reference point** rather than proving an improvement. And a 25-VU run on a
WSL2 dev box says little about a production host under mixed load.

## The tail is worth one look

The 4.29 s maximum is a 15× outlier over the p95. Three candidate explanations,
in the order I would check them:

1. **Cold cache on first touch** — the very first `get_workspace` per VU has to
   build everything. If the outliers cluster at the start of the run, that is
   this, and it is uninteresting.
2. **Contention on the large payload** — 25 concurrent full-map serialisations
   competing for memory and CPU on the dev box. Also expected, and it would
   scale down on real hardware.
3. **Something genuinely occasional** in the workspace assembly — this is the one
   worth ruling out.

The cheap way to distinguish them: re-run with `k6 --summary-trend-stats` including
`p(99)`, and check whether the outliers are front-loaded. If the p99 is close to
the p95 and the slow calls are all early, it is (1) and there is nothing to do.

## Not a blocker

Nothing here changes the Beta assessment. The measured budget (`MAXMS=2000`
server-side) is deliberately looser than the ~200 ms client-side target in the
requirements, because the client target covers a local editor operation, not a
full map load over HTTP. On that basis `get_workspace` is within budget at p95
and the rest of the read path has substantial headroom.

## Reproducing

```
make load-seed        # seeds the large map + REST token
make jmeter           # or: make load-k6
```

See `README.md` for parameters. Raising `VUS` is the obvious next experiment;
`OPLOG` sizes the operation log if `get_operations` is the endpoint under
suspicion.
